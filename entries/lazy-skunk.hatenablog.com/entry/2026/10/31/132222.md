## Actions の設定も見直してみる

これまでは GitHub Actions に `actions/checkout@v7` のような大まかなバージョン指定を書いていた。Dependabot に更新 PR も作ってもらっているし、あまり深く考えずにそのまま使っていた。

そんなとき Twitter で GitHub Actions の設定もしっかりした方がよいという投稿を見かけた。GitHub 公式からも Actions のロックファイルについての記事が出ていて、自分の設定も見直してみようと思った。最近はサイバー攻撃の話もよく見かけるし…。

`@v7` のような指定だと、実行時にそのタグが指すコードが使われる。参照先が悪意のあるコードに差し替えられても、自分の YAML は変わらないまま実行されてしまう可能性があるのはいけませんね。

Actions にもロックファイルを作れるんだなと思って調べる中で、YAML にコミット SHA を直接書いて固定する方法も思い出した。

どちらも使うコードを固定する方法だけど何が違うんだ。自分にはどっちが合うのか調べてみる。

Dependabot に更新 PR を作ってもらう運用はそのままに、使う Action もちゃんと固定したい。その辺を両立できるとよさそう。

## SHA で固定する方法

まずは知っていた方からおさらい。タグの代わりにコミット SHA を書く。

```yaml
- uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
```

これなら後から `v7.0.1` の参照先が変わっても指定したコミットを使い続ける。

SHA を書くと更新できなくなるのかと思ったけど、Dependabot の更新 PR は利用できるみたいで、固定することと更新を止めることは別なのね。

## ロックファイルにまとめる

もう一つが GitHub CLI の拡張 `gh actions-lock`。

[GitHub 公式の一般提供の告知](https://github.blog/changelog/2026-10-28-github-actions-workflow-lockfiles-are-generally-available/)によると Free プランでも使える、ということは自分もいけるのか。
[公式の手順](https://docs.github.com/en/actions/how-tos/secure-your-work/lock-workflow-dependencies)を参考に導入した。

GitHub CLI をインストールして認証した後、拡張機能を入れる。

```powershell
gh auth login
gh extension install github/gh-actions-lock
```

対象のリポジトリーへ移動して実行する。

```powershell
cd D:\Workspace\REPOSITORY
gh actions-lock
```

実行すると `.github/workflows/actions.lock` ができた。ロックファイルが増えるだけかと思ったら、ワークフローの `uses` も書き換わっていた。こっちの差分も確認して、ワークフローと `actions.lock` を一緒にコミットする。

YAML 側はこうなった。

```yaml
- uses: actions/checkout@v7.0.1
```

対応するロックファイルはこんな感じ。一部抜粋。

```yaml
dependencies:
  "actions/checkout@v7.0.1":
    ref: "v7.0.1"
    commit: "sha1-3d3c42e5aac5ba805825da76410c181273ba90b1"
    owner_id: 44036562
    repo_id: 197814629
```

バージョンは YAML、実際に使うコミットはロックファイルで管理する形になる。所有者とリポジトリーの ID も記録される。これはコミットした人の ID ではなく、配布元を識別するための情報。

この ID で配布元が同じかも確認するらしい。[公式の説明](https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles)を見ると、SHA を別ファイルへ移しただけではないのね。

## YAML に SHA を書く方法との違い

どちらも固定したまま Dependabot で更新できるので、違うところを整理してみる。ロックファイルが実行時に適用される環境での比較。

| 主な違い                 | YAML に SHA を書く                                                      | `gh actions-lock` でロックする                  |
| ------------------------ | ----------------------------------------------------------------------- | ----------------------------------------------- |
| 間接依存                 | 直接の SHA 固定だけでは、その Action が使う別の Action まで固定できない | 間接依存もロックの対象                          |
| 配布元の識別             | 所有者名とリポジトリー名を指定                                          | 所有者 ID・リポジトリー ID も記録して検証       |
| 更新時に管理するファイル | YAML の SHA を更新                                                      | YAML のバージョンと `actions.lock` を一緒に更新 |

今回は特に間接依存までロックできる点がよさそうだと思った。[公式ドキュメントの比較](https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles#how-do-lockfiles-compare-with-sha-pinning)も参考にした。

## 自作 Action の共通化も見直した

Python の環境準備は、自作の複合 Action `setup-python-env` にまとめていた。lint と test の両方から呼ぶので共通化していたもの。

```yaml
- uses: ./.github/actions/setup-python-env
```

こっちは `gh actions-lock` を実行したらエラー。該当部分を抜粋する。

```text
✗ local action .github\workflows\lint.yml
  ./.github/actions/setup-python-env runs whatever is in the workspace, so the lockfile can't cover it or the actions it uses; they'll fail when the lockfile is enforced.
    Pass --migrate-local-actions to lock this repo's copy as $/, or --ignore-local-actions to keep ./.
```

エラーの意味は、`./` で参照する自作 Action は実行時の作業ファイル次第なので、その中で使う Action までロックできないということ。そこで案内されているのが、参照するコミットを特定できる `$/` 形式への変更だった。

どちらも自作の複合 Action の `action.yml` を使うけど、次の違いがある。

| 参照方法 | 使うファイル                         | 実行前に `action.yml` を書き換えたら           |
| -------- | ------------------------------------ | ---------------------------------------------- |
| `./`     | チェックアウトした作業中のファイル   | 書き換えた内容を実行する                       |
| `$/`     | ワークフローと同じコミットのファイル | 書き換えは使わず、そのコミットの内容を実行する |

自分の運用では途中でファイルを書き換えていないので実行する処理は変わらないけど、エラーの案内に沿って、まずは次のオプションで `$/` 形式を試してみた。

```powershell
gh actions-lock --migrate-local-actions
```

呼び出しは `uses: $/.github/actions/setup-python-env` に変わり、内部の依存もロックできた。

ただ、ここまでやって、そもそも分ける必要あったか？と思った。中身は `setup-uv` と `uv sync --frozen` の 2 ステップだけ。

一か所直せば済むのはいいけど、読むたびに別ファイルへ飛ぶし、呼び出し方まで考えることになった。この規模なら少しくらい重複していても、その場に書いてある方が分かりやすそう。結局、各ワークフローに直接書くことにした。

```yaml
- uses: astral-sh/setup-uv@v8.1.0

- run: uv sync --frozen
```

この後に lint や test の処理が続くので、ワークフローを開けば環境準備から実行まで追える。不要になった `action.yml` は削除して、`gh actions-lock` を再実行した。

ロックを試すつもりが、ついでに要らなそうな共通化も片付いたのは良い副産物だったかも。

## ロックしても確認は必要

ロックする時点で配布元が侵害されていた場合は、悪意のあるコードを固定してしまう可能性がある。公式コマンドが取得した値だからといって、コードの安全性まで保証してくれるわけではない。新しいバージョンへ更新するときも同じ。
