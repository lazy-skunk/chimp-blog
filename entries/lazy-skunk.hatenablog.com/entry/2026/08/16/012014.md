## はじめに

モジュールの結合は、弱ければ弱いほどよいと思い込んでいた。でも処理を分けた結果、別の複雑さを持ち込むこともあるらしい。弱くすればいいって話でもないのか。

『[ソフトウェア設計の結合バランス 持続可能な成長を支えるモジュール化の原則](https://book.impress.co.jp/books/1124101149)』の「第5章 構造化設計におけるモジュール結合」を読み、サンプルコードを作りながら理解を整理してみる。（とはいえ、実は一周読んでいるので、第6章以降の情報がうっかり反映されているかもしれない。）

書名にもあるとおり、大切なのは「結合バランス」らしい。（ということは今まで書いてきたコードには誤った考えが反映されているかもしれないぞ…。）

モジュール結合に関する記事はいくつか読んだけど、この本の「知識の共有」という観点からの説明が特に印象に残っている。

## モジュール結合とは

モジュール結合は、モジュール同士がどのような知識やデータを介して依存しているかを表す。

モジュール同士が協調する以上、何らかの結合は避けられない。

どのような知識をどのような形で共有しているかを意識すると、変更の影響を考えやすくなるんだなと思った。

## 結合種別の比較

| 種類         | 依存するもの                       | 結合の生じ方                             | 結合強度      | 変更時に起き得ること                     |
| ------------ | ---------------------------------- | ---------------------------------------- | ------------- | ---------------------------------------- |
| 内容結合     | 別モジュールの内部実装             | 非公開の属性やメソッドを直接利用する     | 1（最も強い） | 内部実装の変更で利用側が壊れる           |
| 共通結合     | 複数モジュールが参照する共有状態   | 同じグローバル変数を読み書きする         | 2             | 一方の値の変更が他方の動作に波及する     |
| 外部結合     | 外部システムが定めた形式や規約     | 外部固有の項目名や値の意味を知っている   | 3             | 外部仕様の変更で利用側の修正が必要になる |
| 制御結合     | 呼び出し先の処理を選択する制御情報 | フラグや操作種別を渡して処理を分岐させる | 4             | 分岐の追加や変更の影響を受ける           |
| スタンプ結合 | 必要な値を含むデータ構造全体       | 一部しか使わないオブジェクト全体を渡す   | 5             | データ構造の変更が利用側に波及する       |
| データ結合   | 呼び出し先が必要とする個別の値     | 必要な値だけを引数として渡す             | 6（最も弱い） | 必要な値の変更が引数の定義に波及する     |

※ ここでは、書籍を読んで整理した6種類を相対的に並べている。数値はこの表の中での目安。強い結合がいつも悪く、弱い結合がいつも良いというわけではない。（自戒を込めて）

## 各種結合について

### 内容結合

内容結合は、別モジュールの非公開の属性やメソッドなど、そのモジュールの内部実装を知ったうえで利用する結合。

```python
repository = order_repository.OrderRepository()

methods = dict(inspect.getmembers(repository, predicate=inspect.ismethod))
save_to_database = methods["_save_to_database"]
save_to_database(1)
```

この例では、別モジュールの内部実装に依存していることを分かりやすくするため、あえてリフレクションを使っている。次のように非公開メソッドを直接呼び出す場合も内容結合。

```python
repository._save_to_database(1)
```

念のため補足すると、内容結合かどうかは呼び出し方ではなく、別モジュールの内部実装を知り、それに依存しているかで決まる。

利用側は、`OrderRepository` の内部メソッド `_save_to_database` の名前を知っている。例えば、内部の整理でこの名前が変われば、利用側にも影響する。

デバッグやテストなど、限定された場面で使うことはあると思う。でも、それ以外にどんな使い道があるのかは今のところよく分かっていない…。

### 共通結合

共通結合は、複数のモジュールが同じグローバル変数や共有領域を参照する結合。

```python
# shared_tax.py
tax_rate = 0.10

# reduced_price.py
def calculate(subtotal: int) -> float:
    shared_tax.tax_rate = 0.08
    return subtotal * (1 + shared_tax.tax_rate)

# standard_price.py
def calculate(subtotal: int) -> float:
    return subtotal * (1 + shared_tax.tax_rate)
```

軽減税率の計算のために `reduced_price` が共有税率を8%へ変更すると、その後に呼ばれる `standard_price` も8%で計算されてしまう。呼び出し順で結果が変わってしまうのが困るところ。

一方で、読み取り専用の設定やロガーなど、複数のモジュールで共有することが合理的な場合もある。

[共通結合のサンプルコード全体](https://github.com/lazy-skunk/sandbox/tree/main/playground/balancing_coupling/module_coupling/common_coupling)

### 外部結合

外部結合は、外部 API のレスポンス形式、ファイル形式、データベーススキーマなど、自分で制御できない外部仕様の知識に依存する結合。

```python
def is_paid(order_id: int) -> bool:
    result = external_system.request_payment(order_id)
    return result["result_code"] == "OK"

def create_receipt(order_id: int) -> str:
    result = external_system.request_payment(order_id)
    return f"{result['amount']}円"
```

この二つの処理は同じ結果オブジェクトを共有しているわけではない。共有しているのは、外部システムの結果に `result_code` や `amount` という項目があるという知識。

外部結合は避けられない場合が多い。外部仕様が変わるたびにあちこち直すのは面倒なので、アダプターなどの境界に集めておくのがよさそうだな。

[外部結合のサンプルコード全体](https://github.com/lazy-skunk/sandbox/tree/main/playground/balancing_coupling/module_coupling/external_coupling)

### 制御結合

制御結合は、呼び出し側がフラグや操作種別などの制御情報を渡し、呼び出し先の実行する処理を選択する結合。

```python
def process(order_id: int, gift_wrap: bool) -> None:
    print(f"注文 {order_id} を受付")
    if gift_wrap:
        print(f"注文 {order_id} をギフト包装")
    print(f"注文 {order_id} を発送")

process(order_id=1, gift_wrap=False)
process(order_id=2, gift_wrap=True)
```

どちらも注文の受付と発送を行うけど、`gift_wrap` によって包装処理の有無が変わる。

フラグの意味が分かりやすくて分岐も少ないなら、これで十分そう。

ただし、フラグが増え、呼び出し側が呼び出し先の内部構造を詳しく知る必要が出てきた場合は、そろそろ設計を見直す時なのかもしれないな。

[制御結合のサンプルコード全体](https://github.com/lazy-skunk/sandbox/tree/main/playground/balancing_coupling/module_coupling/control_coupling)

### スタンプ結合

スタンプ結合は、呼び出し先がデータ構造の一部しか使わないにもかかわらず、オブジェクトやレコード全体を渡す結合。

```python
@dataclass(frozen=True)
class Order:
    order_id: int
    customer_name: str
    shipping_address: str
    items: tuple[str, ...]
    total: int

def print_label(order: Order) -> None:
    print(f"注文番号: {order.order_id}")
    print(f"宛名: {order.customer_name}")
    print(f"配送先: {order.shipping_address}")
```

配送ラベルに必要なのは注文番号、宛名、配送先だけ。でも、商品や合計金額も含む `Order` 全体を渡している。

これなら引数を一つにできるし、「配送は注文を扱う」ことも表現できる。一方、テストのために使わない商品や金額まで用意するのは面倒だな。そう感じるなら、依存範囲が広すぎるのかもしれない。

[スタンプ結合のサンプルコード全体](https://github.com/lazy-skunk/sandbox/tree/main/playground/balancing_coupling/module_coupling/stamp_coupling)

### データ結合

データ結合は、呼び出し先が必要とする個別の値だけを引数として渡す結合。

```python
def print_label(
    order_id: int,
    customer_name: str,
    shipping_address: str,
) -> None:
    print(f"注文番号: {order_id}")
    print(f"宛名: {customer_name}")
    print(f"配送先: {shipping_address}")
```

必要な値がシグネチャから明確になり、テストの準備も小さくできる。一方、必要な値が増えるたびに引数が増え、呼び出し箇所の修正が必要になる。

引数が増えるのも、使わない情報まで渡すのも気になる。オブジェクト全体を扱う必要があるか、変更やテストのしやすさを見て決めるしかないのかな。

[データ結合のサンプルコード全体](https://github.com/lazy-skunk/sandbox/tree/main/playground/balancing_coupling/module_coupling/data_coupling)

## まとめ

結合の種類だけで実装の良し悪しは決められないんだな。結合を弱めようとして、かえってコードを複雑にしてしまうこともある。

何を一緒に扱い、どんな変更を受けるのか。実装やテストの分かりやすさも見て選びたい。疎結合や高凝集は、その結果を後から説明する言葉なのかもしれない。言葉の方を先に目標にしないようにしないとな。
